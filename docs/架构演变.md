# 架构演变历程

> 从单机原型到分布式即时通信系统的 7 次演进。

---

## 阶段一：单机原型 — Redis 内存存储

**架构**：单 `server` + 单 `client`，纯内存运行。

**数据流**：
```
client ──→ server ──→ Redis（全部消息）
```

**问题**：Redis 是内存数据库，机器重启后历史消息全部丢失。快速原型验证阶段可用，但无法作为生产存储。

---

## 阶段二：单机 + SQLite 本地持久化

**方案**：在服务端嵌入 SQLite，消息同时写入 Redis（缓存最近 N 条）和 SQLite（全量持久化）。引入 `TaskPool` 单线程池，SQLite 写操作异步执行，不阻塞消息发送线程。

**新增文件**：`sqlsave.hpp`、`task_pool.hpp`、`redis_inbox.hpp`

**数据流**：
```
client ──→ server
              ├── Redis conv ZSET（最近 10 条缓存）
              └── TaskPool ──→ SQLite（异步全量持久化）
```

**问题**：所有客户端连接都打到同一台服务器。单机 CPU 被网络 I/O + 消息转发占满，无法通过扩容提升吞吐。

---

## 阶段三：手动集群 — 静态配置多节点

**方案**：将服务端水平复制为多份，每个节点启动时通过代码中写死的 `ip:port` 列表连接其他节点。客户端启动时手动选择一个节点地址连接。

**数据流**：
```
client ──→ node-1 ←──→ node-2（配置文件预配）
client ──→ node-2
```

**问题**：无法动态扩容。访问量暴增时需修改配置文件、重启所有节点，导致服务中断。节点数量少时问题不明显，规模越大越难维护。

---

## 阶段四：动态注册发现 — Redis Pub/Sub + Nginx 网关

**方案**：

- 每个节点启动时将自己的 `node_id:port` 写入 Redis `cluster:nodes` hash，通过 Pub/Sub 广播 `cluster:node_join` 事件
- 已有节点订阅 `cluster:*` 频道，发现新节点后自动建立 peer 连接
- 引入 Nginx Stream L4 层负载均衡（`least_conn` 策略），客户端统一连接 Nginx 端口，不再感知后端拓扑

**新增文件**：`nginx.conf`

**数据流**：
```
client ──→ Nginx Stream (8877)
                │ least_conn
           ┌────┼────┐
      node-1  node-2  node-3
           └────┼────┘
                │ Redis Pub/Sub
         cluster:node_join / cluster:nodes
```

**解决**：
- 新节点上线 → 自动注册 → 集群感知 → 流量接入，零配置修改
- Nginx least_conn 补偿用户连接分布不均的问题

**问题**：SQLite 依附在各节点内部，每个节点各写各的盘，导致：
- 消息散落在不同机器的 SQLite 文件中，无法全局拉取
- 同一聊天对的 seq_id 在不同节点上可能乱序
- 节点宕机导致该节点上存储的消息丢失

---

## 阶段五：存储拆分 — 独立 SQLite 持久化服务

**方案**：将 SQLite 从 server_node 中拆出，独立为 `sqlite_service` 进程。所有节点的存储请求通过 RPC 转发给 `sqlite_service` 串行执行。server_node 不再直接接触存储。

**新增文件**：`server_node.cpp`、`sqlite_service.cpp`

**数据流**：
```
client ──→ Nginx ──→ server_node-1 ──RPC──→ sqlite_service ──→ SQLite
client ──→ Nginx ──→ server_node-2 ──RPC──→ sqlite_service ──→ SQLite
client ──→ Nginx ──→ server_node-3 ──RPC──→ sqlite_service ──→ SQLite
```

**测试数据**：
| 场景 | QPS |
|------|-----|
| RPC 单机 echo | ~20,000 |
| 消息转发（含持久化） | **~170 msg/s** |

**问题**：性能断崖式下跌。`echo` 是纯 RPC 转发无存储，20K QPS；加上一次消息持久化骤降到 170 msg/s。根因：
- **全部串行**：所有节点的所有写入压在单线程 SQLite 上，锁竞争严重
- **调用频繁**：每条消息触发一次 RPC 调用 + 一次 SQLite INSERT，往返次数翻倍
- **同步等待**：server_node 要等到 `sqlite_service` 返回才能响应客户端

---

## 阶段六：MySQL + 批量异步写入

**方案**：

- 存储层从 SQLite 迁移到 MySQL，利用 MySQL 的并发读写能力
- 写操作内嵌到 server_node 中直连 MySQL 执行，不再走 RPC 调用 `sqlite_service`
- 引入 `MessageBatchSaver`：消息先入内存队列，攒批 50 条或 100ms 超时后批量 `BEGIN + INSERT + COMMIT`
- `sqlite_service` 退化为仅处理读操作（拉取历史、好友验证等）
- MySQL 连接池（hardware_concurrency 个连接，本机 16 个）

**新增文件**：`mysql_save.hpp`、`batch_saver.hpp`

**数据流**：
```
client ──→ Nginx ──→ server_node
                         ├── Snowflake（本地生成 seq_id）
                         ├── batch_saver.push(msg)  ──→ 批量写入 MySQL
                         ├── deliver_message
                         │    ├── 本地在线 → 直接 push
                         │    ├── 缓存命中 → RPC 跨节点转发
                         │    └── 未命中 → Redis HGET → 缓存 → 转发
                         └── sqlite_service（仅读：历史/好友/用户校验）
```

**测试数据（单机 16 连接，1KB payload）**：
| 场景 | QPS |
|------|-----|
| 消息转发（含 user_exists MySQL 查询） | ~13,000 |
| 消息转发（去 user_exists，离线场景） | **~20,000** |
| 消息转发（跨节点在线） | **~10,800** |

**对比阶段五**：从 170 msg/s 到 13K QPS，提升 **~76x**。

**问题**（5 节点实测仅 11.5K QPS，远低于预期）：

| 怀疑方向 | 排查结论 |
|---------|---------|
| MySQL 写锁竞争 | MySQL 实测 ~13,814 QPS（读+写），尚未达到上限，不是主要瓶颈 |
| Nginx 负载不均 | 连接未散开，流量集中在 1-2 个节点。换短连接压测后缓解 |
| **Redis 单点** | 每条消息产生 1 次 INCR（seq_id）+ 1 次 HGET（位置路由），11K QPS 时 Redis 命令数约 **109K ops/sec**，已接近单核瓶颈——这是被忽视的真正瓶颈 |

---

## 阶段七：去 Redis 化 + 本地缓存 + 短连接池

**方案**：

1. **Snowflake 全局 ID**：本地生成 64-bit 唯一 ID（41-bit 毫秒戳 + 10-bit node_id + 12-bit 序列号），替代 Redis INCR。去掉了每条消息一次网络 RTT。
2. **本地 user_location 缓存**：用户上线时，位置信息写入本地 `g_location_cache`。消息路由优先查缓存，命中则零网络开销，仅缓存未命中时回退到 Redis HGET。
3. **去除冗余 MySQL 查询**：`handle_send_message` 中的 `user_exists` 校验在真实场景不可能触发（客户端无法向不存在的用户发消息），去掉后 QPS +52%。
4. **MySQL 表加索引**：`messages` 表增加 `idx_conv (from_user, to_user, seq_id)`，加速历史拉取。
5. **短连接池压测**：改用独立 io_context + 独立连接的客户端模式，消除 Nginx least_conn 长连接粘连的问题。

**新增文件**：`snowflake.hpp`、`stress_test.cpp`、`echo_server.cpp`

**测试数据（压测报告终版）**：
| 场景 | QPS | 延迟(P50) | 说明 |
|------|-----|-----------|------|
| echo MSGPACK | **54,558** | 1 ms | RPC 框架基准 |
| echo RAW（裸二进制） | **135,368** | 0.5 ms | 纯框架开销 7.4 μs |
| 消息转发（含 MySQL 批量写，离线） | **20,269** | 5 ms | 去 user_exists，接收方不在线 |
| 消息转发（跨节点 RPC 转发，在线） | **10,825** | 5 ms | sender/receiver 在不同节点 |

**核心结论**：
- 阶段六的 11.5K → 最终 13K "提升不大"，是因为 **真正的瓶颈从 Redis 转移到了序列化**（nlohmann::json 占 CPU 60%），而非存储层
- 序列化才是当前吞吐上限的决定因素，换 Protobuf 预期 2-3 倍提升
- 离线场景 20K QPS 证明 MySQL 批量写入在高并发下不是瓶颈

---

## 各阶段 QPS 演进汇总

```
阶段一（单机 Redis）      不可测量（纯内存，丢数据）
阶段二（单机 SQLite）     可用但无压测数据
阶段三（手动集群）        ~同单机（未解决存储问题）
阶段四（Redis 发现+Nginx）     ~同单机
阶段五（SQLite 拆分）      170 msg/s    ← 串行写入瓶颈
                           ↓ +76x
阶段六（MySQL + 批量写）   11,500       ← 去串行化
                           ↓ +13%
阶段七（Snowflake + 本地缓存） 13,000   ← 瓶颈转移至序列化
                           ↓ +4x（预期）
换 Protobuf（理论）        50,000+     ← 去掉序列化瓶颈
```

## 关键设计决策

| 决策 | 阶段 | 权衡 |
|------|------|------|
| 自研 RPC 而非 gRPC | 全部 | 代码量 600 行，可控；功能不如 gRPC 完善 |
| Redis Pub/Sub 而非 ZK/etcd | 四 | ZK 太重，维护成本高；Redis 已存在，零额外依赖 |
| MySQL 直连 + 批量写 | 六 | 写入快，但耦合了存储逻辑；sqlite_service 退化为读服务 |
| Snowflake 替代 INCR | 七 | 去网络 RTT + 去单点；需 node_id 全局不冲突 |
| MessagePack 而非 JSON 文本 | 七前 | 二进制更紧凑更快；调试时不如 JSON 直观 |
