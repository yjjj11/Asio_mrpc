# 架构演变历程

> 从单机原型到分布式即时通信系统的 5 次演进。
> 每个阶段包含：背景、实现细节、数据流、选型考量、面试 FAQ。

---

## 阶段一：单机原型 — 纯内存，无持久化

### 背景

快速验证自研 RPC 框架的可用性。只实现了最核心的聊天功能：用户登录、在线列表、发消息。所有数据存在 `std::unordered_map` 中，服务重启即丢失。

### 实现细节

最早的 `server.cpp`（commit `ee9bcce`）的核心数据结构：

```cpp
std::unordered_map<std::string, std::shared_ptr<connection>> g_online_users;
std::shared_mutex g_online_mutex;
std::unordered_map<std::string, P2PAddr> g_user_p2p_addr;
```

注册了 7 个 RPC handler：`user_login`、`get_online_users`、`user_logout`、`send_message`、`send_group_message`、`report_p2p_port`、`request_p2p_connect`。

`send_message` 逻辑极简单：

```cpp
bool send_message(conn, from_user, to_user, message) {
    std::shared_lock lock(g_online_mutex);
    auto it = g_online_users.find(to_user);
    if (it != g_online_users.end()) {
        it->second->async_call(..., "on_message", from_user, message);
    }
    return true;
}
```

不落盘、不排队、不校验。找到目标就推送，找不到就丢弃。

### 问题

服务端重启后所有数据归零。P2P 地址信息丢失、消息不落地。只能验证 RPC 通信，无法作为真实聊天工具使用。

### 面试 FAQ

**Q: 最开始为什么不做持久化？**

> A: 初期目标是验证自研 RPC 框架的功能完整性。先跑通核心链路（登录→发消息→收消息），持久化是工程问题不是框架问题，放到后面迭代解决。这也是快速原型的核心思路——先让东西跑起来。

## 阶段二：双层存储 — Redis 缓存 + SQLite 异步持久化

### 背景

需要解决消息持久化问题，同时希望保持"进入聊天能看到最近几条消息"的体验。

### 选型考量：为什么是 Redis + SQLite 双层？

**Redis** 天然适合做最近消息缓存：
- ZSET 按 score（seq_id）排序，ZREVRANGE 即可拿到最新 N 条
- TTL 自动过期旧数据
- 项目已在使用 Redis，零额外部署成本

**SQLite** 做全量持久化：
- 嵌入式，无需独立部署
- 单机场景写入够用
- 与 Redis 配合：Redis 扛读（热点），SQLite 扛写（全量）

### 实现细节

核心引入三个文件（commit `6227d09`）。

**① RedisInbox（redis_inbox.hpp） — ZSET 操作**

```
key 格式:   conv:<user_a>:<user_b>   （字典序排列，A→B 与 B→A 同 key）
value 格式: from|to|msg              （管道符分隔）
score:      seq_id                   （全局递增 ID）
```

主要方法：

| 方法 | Redis 命令 | 用途 |
|------|-----------|------|
| `next_seq_id()` | `INCR global:msg_seq` | 生成全局递增 ID |
| `push_conv(a,b,seq_id,from,to,msg)` | `ZADD conv:A:B score value` | 写入消息到 ZSET |
| `pull_recent(a,b,limit)` | `ZREVRANGE conv:A:B 0 limit` | 拉取最近消息 |
| `trim_conv(a,b,keep=10)` | `ZCARD` + `ZPOPMIN` | 超限后弹出旧消息 |

**② TaskPool（task_pool.hpp） — 单线程异步写入器**

```cpp
class TaskPool {
    std::vector<std::thread> workers_;  // 构造时传 1，单线程
    std::queue<std::function<void()>> tasks_;

    void post(Func&& f) {
        {   std::lock_guard lock(mtx_);
            tasks_.push(std::move(f));  }
        cv_.notify_one();
    }
};
```

**关键设计**：单线程 + 队列。SQLite 写操作不并发执行，天然消除锁竞争。调用者 `post()` 后立即返回，不阻塞消息发送线程。

**③ SqliteSaver（sqlsave.hpp） — SQLite ORM**

```cpp
// 异步写入（由 TaskPool 线程调用）
void save(const std::vector<Message>& msgs) {
    auto storage = get_storage();
    storage->transaction([&] {
        for (auto& m : msgs) storage->replace(m);
        return true;
    });
}

// 增量拉取（由 RPC handler 同步调用）
std::vector<Message> load_after(user, after_seq_id, limit);
std::vector<Message> load_latest(user, limit);
```

### 数据流

```
send_message(from, to, msg)
  │
  ├─ 1. Redis INCR global:msg_seq                → seq_id
  ├─ 2. Redis ZADD conv:A:B seq_id "from|to|msg" → 写入 ZSET
  ├─ 3. Redis ZCARD conv:A:B > 10？
  │      └─ ZPOPMIN 弹出最旧 → evicted[]
  │           └─ TaskPool.post → SQLite.save(evicted)
  │                              （后台线程异步执行）
  └─ 4. 目标在线？ → async_call("on_message")
```

关键触发条件：**SQLite 仅在 conv ZSET 超过 10 条时才触发**。最近的 10 条始终在 Redis 里，随时可读。

```
时间线：
t1  msg#1  → ZADD → ZCARD=1  → 不触发
t2  msg#2  → ZADD → ZCARD=2  → 不触发
...
t10 msg#10 → ZADD → ZCARD=10 → 不触发
t11 msg#11 → ZADD → ZCARD=11 → 超出！ZPOPMIN 弹出 msg#1
                                 │
                                 └→ TaskPool.post → SQLite.save(msg#1)
```

### 问题

所有连接都打在同一台服务器上。单机 CPU 被网络 I/O + JSON 序列化 + 消息转发占满，无法通过加机器提升吞吐。

### 面试 FAQ

**Q: 为什么阈值设 10 条？**

> A: 经验值。进入聊天时能看到 10 条上下文基本够用，同时控制了 SQLite 的写入频率——10 条消息后才写一次盘。后来压测也发现这个值对性能影响不大，瓶颈不在这里。

**Q: TaskPool 为什么是单线程？**

> A: SQLite 本身就不支持并发写入（锁表），多线程写反而更慢。单线程队列消费 + 条件变量唤醒的方案最简单可靠。

**Q: 消息还在 Redis 里没刷到 SQLite，服务宕机丢多少？**

> A: 丢最近最多 10 条。每条聊天独立 ZSET，某聊天如果只有 3 条消息，那 3 条都在 Redis 里，宕机全丢。这个阶段定位是功能验证，没做 crash recovery。生产化的话可以加 WAL 或双写。

## 阶段三：手动集群 —— Zookeeper → 静态配置

### 背景

单机容量不够，需要多台服务器分担连接。

### 尝试：Zookeeper 方案

从 commit `178ac3c` 可以看到引入过 Zookeeper：

```
third/include/ZookeeperUtil.hpp    // ZK C API 封装
```

但 Zookeeper 方案在后续 commit（`6227d09`）中被完全删除，原因是：

- **太重**：ZK 需要独立部署 3-5 节点集群，运维成本高
- **C API 难用**：手动管理 watcher 和 session，开发效率低
- **规模不匹配**：项目初期只有 2-3 个节点，ZK 的强一致性、leader 选举功能完全用不上

**教训**：技术选型要考虑项目实际规模，不要预先引入重量级组件。

### 替代：静态配置

删除 ZK 后，手动在代码中预设其他节点的 `ip:port`，启动时逐个连接：

```cpp
g_peer_conns["node-2"] = client.connect("192.168.1.2", 8882);
g_peer_conns["node-3"] = client.connect("192.168.1.3", 8883);
```

客户端启动时手动指定一个服务器地址。

### 问题

- **扩容要重启**：加节点要改配置、重新编译、重启所有节点，有停机时间
- **客户端感知拓扑**：客户端要知道节点地址列表，选错连不上

### 面试 FAQ

**Q: ZK 在分布式系统里很常见，你们为什么不用了？**

> A: 杀鸡不用牛刀。我们需要的只是"新机器上线，通知老机器"这个功能，ZK 的强一致性、leader 选举、分布式锁对我们来说都是过剩能力。后来用 Redis Pub/Sub 替换了 ZK，因为 Redis 已经在项目里，一行 `PUBLISH` 就能做到。

**Q: 不用 ZK 之后，静态配置方案能支撑多少节点？**

> A: 实测 5 节点。静态配置的扩展上限取决于节点间全连接的网络复杂度（O(n²) 连接），而不是配置维护的复杂度。超过 10 个节点建议换服务网格或 Sidecar 模式。

## 阶段四：存储拆分 + Redis Pub/Sub 发现 + Nginx 网关

### 背景

阶段三遗留了三个核心问题：
1. **存储混乱**：每个节点各带一份 SQLite，消息散落在不同机器，全局拉取和顺序无法保证
2. **扩容困难**：节点列表硬编码，加机器要重启
3. **客户端耦合**：客户端要感知节点地址

同时架构上需要将「存储」和「转发」两个职责拆开，使转发层可以无状态水平扩展。

### 实现细节

这是项目最大的一次架构重构（commit `4b4172e`）。

**① 服务拆分：server_node + sqlite_service**

```
┌─ server_node（业务转发）───┐     ┌─ sqlite_service（数据持久化）─┐
│ 用户登录/登出              │     │ 注册/验证用户               │
│ 消息路由/转发              │     │ 检查用户是否存在             │
│ 好友管理                   │ RPC │ 好友增删查                  │
│ 在线状态广播               │────►│ 消息存储/拉取               │
└───────────────────────────┘     └────────────────────────────┘
```

`sqlite_service` 将所有请求**串行化**（单 SQLite 连接），保证多节点数据一致性。代价是所有写入都要过 RPC。

**② Redis Pub/Sub 自动发现 — 替换 ZK / 静态配置**

节点启动时的注册流程：

```cpp
// 1. 读取已有节点
redisReply* reply = redisCommand(g_redis, "HGETALL cluster:nodes");
for (size_t i = 0; i + 1 < reply->elements; i += 2) {
    connect_peer(reply->element[i]->str, host, port);
}

// 2. 宣告自己上线
redisCommand(g_redis, "HSET cluster:nodes %s %s", g_node_id, "127.0.0.1:8881");
redisCommand(g_redis, "PUBLISH cluster:node_join %s=%s", g_node_id, "127.0.0.1:8881");
```

订阅方收到 `cluster:node_join` 后，从 Redis 获取新节点地址，调用 `connect_peer()` 建立双向 RPC 连接。节点下线时：

```cpp
// 信号处理 SIGINT/SIGTERM
redisCommand(g_redis, "HDEL cluster:nodes %s", g_node_id);
redisCommand(g_redis, "PUBLISH cluster:node_leave %s", g_node_id);
```

**③ Nginx Stream（L4）负载均衡**

```nginx
stream {
    upstream chat_backend {
        least_conn;
        server 127.0.0.1:8881;
        server 127.0.0.1:8882;
        server 127.0.0.1:8883;
        server 127.0.0.1:8884;
        server 127.0.0.1:8885;
    }
    server { listen 8877; proxy_pass chat_backend; }
}
```

**选 least_conn 而非 round-robin**：长连接场景下，用户活跃度不均。某个"话痨"用户会占用大量消息转发资源，least_conn 能把新连接分配给当前负载最低的节点。

### 数据流（消息发送）

```
send_message(from, to, msg)
  │
  ├─ RPC: user_exists(to)                 ← sqlite_service，SQL SELECT
  ├─ Redis: INCR seq:A:B                  ← 全局递增 seq_id
  ├─ RPC: notify(save_messages, msg)      ← sqlite_service，SQL INSERT
  │
  └─ deliver_message(from, to, msg)
       ├─ g_local_users.find(to)？        ← 本节点在线 → 直接 push
       ├─ Redis: HGET user_location to    ← 找目标节点
       └─ RPC: remote_deliver → 目标节点  ← 跨节点转发
```

一条消息至少触发：**3 次 RPC + 2 次 Redis 命令** = 5 次网络往返。

### 测试数据

| 场景 | QPS | 说明 |
|------|-----|------|
| echo（纯 RPC 转发，无存储） | ~20,000 | 框架基底性能 |
| 完整消息链路（含存储） | **~170 msg/s** | 加了存储后暴跌 **100x+** |

**170 msg/s 的根因拆解（每消息耗时）：**

```
[server_node]         [sqlite_service]       [Redis]
    │                       │                   │
    ├─ user_exists(RPC)────►│                   │
    │◄───────true──────────┤                   │
    │                       │                   │
    ├─────INCR─────────────────────────────────►│
    │◄──────seq_id─────────────────────────────┤
    │                       │                   │
    ├─ save_messages(RPC)──►│                   │
    │                       ├── SQLite INSERT   │ ← 全部串行，等待 IO
    │◄────────ok───────────┤                   │
    │                       │                   │
    ├─────HGET─────────────────────────────────►│
    │◄────target_node─────────────────────────┤
    │                       │                   │
    └─ remote_deliver(RPC)─►│(跨节点转发)        │
```

每条消息 3 次 RPC 调用 + 2 次 Redis 命令，任何一步阻塞整条链路都要等。串行化的 sqlite_service 成为了绝对瓶颈。

### 面试 FAQ

**Q: 170 msg/s 是不是低得离谱？怎么定位的？**

> A: 做过链路分解：纯 echo 20K → 加一次 RPC user_exists 降到 ~10K → 加 Redis INCR 降到 ~5K → 加 SQLite INSERT 直接掉到 170。最终确认 SQLite 单线程串行写入 + 每消息 3 次 RPC 往返是主因。这个实验也证明了**串行化写入在分布式系统中是灾难**，后续立刻换了 MySQL + 批量写入。

**Q: Redis Pub/Sub 在节点发现场景下有什么缺陷？**

> A: Pub/Sub 不保证消息可靠投递——订阅者离线期间的消息会丢失。但在集群发现这个场景不是问题，因为新节点上线后，老节点可以通过读 `cluster:nodes` hash 补全节点列表。最终一致性就够了。

**Q: Nginx 为什么选 L4 而不是 L7？**

> A: 我们的 RPC 协议是基于 Asio 的自定义 TCP 协议，不是 HTTP。Nginx Stream 工作在 L4，直接透传 TCP 包，不做应用层解析，延迟最低、吞吐最高。如果用 L7（HTTP），必须改协议、加 HTTP 头开销，得不偿失。

## 阶段五：MySQL + 批量异步写入 + 本地缓存 + 容器化

### 背景

阶段四从 20K 掉到 170 msg/s 的教训说明：**串行化写入 + 每消息多次网络往返 = 架构级错误**。需要根本性重构存储层，核心思路三个：

1. 并发写入替代串行写入
2. 减少 RPC 调用次数
3. 去掉链路中不必要的校验

### 选型考量

**为什么是 MySQL？**

| 方案 | 优缺点 |
|------|--------|
| **MySQL** | 支持并发读写，有连接池，生态成熟，hiredis/mysqlclient 已存在 |
| SQLite（原地优化） | 多进程写会锁库，单线程写入上限约 5K TPS 无法突破 |
| PostgreSQL | 性能更好，但需要额外装 libpq，部署更重 |

关键：MySQL 连接池（默认 16 连接）可以配合 server_node 的 io_context 线程池实现并行写入，彻底解决串行化问题。

### 实现细节

**① MySQL 连接池（mysql_save.hpp）**

```cpp
class MySQLPool {
    std::queue<MYSQL*> conns_;
    size_t pool_size_;

    MYSQL* borrow() {
        std::unique_lock lock(mtx_);
        cv_.wait(lock, [this]{ return !conns_.empty(); });
        auto conn = conns_.front(); conns_.pop();
        return conn;
    }
    void release(MYSQL* c) {
        std::lock_guard lock(mtx_);
        conns_.push(c); cv_.notify_one();
    }
};
```

RAII 封装 `AutoConn` 保证连接一定会归还，避免泄露。池大小默认 `min(hardware_concurrency(), 16)`，本机 16。

**② 消息批量异步写入（batch_saver.hpp）**

核心设计：**攒批（batch）+ 异步（async）**

```cpp
void push(Message msg) {
    std::lock_guard lock(mtx_);
    batch_.push_back(std::move(msg));
    if (batch_.size() >= 50)      // 攒够 50 条
        cv_.notify_one();         // 唤醒 flush 线程
}

void flush_loop() {
    while (true) {
        std::vector<Message> msgs;
        {
            std::unique_lock lock(mtx_);
            cv_.wait_for(lock, 100ms, [this]{  // 最多等 100ms
                return batch_.size() >= 50;
            });
            msgs.swap(batch_);
        }
        if (!msgs.empty())
            db_->save(msgs);      // BEGIN + INSERT×N + COMMIT
    }
}
```

**50 条 / 100ms 设计权衡**：

| 参数 | 设大（如 500 条 / 1s） | 设小（如 5 条 / 10ms） |
|------|------------------------|------------------------|
| 吞吐 | 更高（事务少） | 更低（事务频繁） |
| 延迟 | 更高（攒批久） | 更低（刷出快） |
| 风险 | 宕机丢 500 条 | 宕机丢 5 条 |

50/100ms 是平衡点：50 条不超过 MySQL `max_allowed_packet`（默认 64MB），100ms 用户几乎无感知。

**③ Snowflake 全局 ID（snowflake.hpp）**

```cpp
uint64_t next_id() {
    std::lock_guard lock(mtx_);
    uint64_t now = ms_since_epoch();
    if (now == last_ms_) {
        seq_ = (seq_ + 1) & 0xFFF;   // 12-bit sequence
        if (seq_ == 0) {              // 当前 ms 用完
            while (ms_since_epoch() == last_ms_) {}  // 自旋等下一 ms
        }
    } else {
        seq_ = 0;
    }
    last_ms_ = now;
    return (now << 22) | (node_id_ << 12) | seq_;
}
```

**为什么替代 Redis INCR？**
- 去掉每条消息一次网络 RTT
- 去掉 Redis 单点对 seq_id 可用性的影响
- 本地生成，0 网络开销

**④ 三级缓存路由**

```cpp
static void deliver_message(...) {
    // 第 1 级：本节点在线
    {   std::shared_lock l(g_local_mutex);
        auto it = g_local_users.find(to);
        if (it != g_local_users.end()) {
            it->second->async_call(..., "on_message", ...);
            return;   // 零网络
        }
    }
    // 第 2 级：本地缓存
    {   std::shared_lock l(g_location_mutex);
        auto it = g_location_cache.find(to);
        if (it != g_location_cache.end()) {
            RPC remote_deliver → it->second;  // 零 Redis
            return;
        }
    }
    // 第 3 级：Redis 回退
    redisReply* reply = redisCommand(g_redis, "HGET user_location %s", to);
    g_location_cache[to] = reply->str;  // 回填缓存
    RPC remote_deliver → reply->str;
}
```

**关键**：缓存命中时零 Redis 访问。只有新上线的用户或缓存过期才回退到 Redis HGET。

**⑤ 去掉冗余 user_exists**

```cpp
// 删除前：
auto ret = g_sqlite_conn->call<bool>("user_exists", to_user);
if (!ret.value()) return 0;        // 每次消息都查 MySQL！

// 删除后：
uint64_t seq_id = g_snowflake->next_id();
g_batch_saver.push(Message{...});
deliver_message(from, to, msg, seq_id, timestamp);
```

这个校验在真实场景**永远不可能触发**——客户端注册用户后才能发消息，对方必然是存在的。去掉后 QPS 从 13K 提升到 20K（+52%）。

### 完整数据流

```
handle_send_message(from, to, msg)
  │
  ├─ Snowflake::next_id()             ← 本地，0 网络
  ├─ g_batch_saver.push(msg)          ← 入内存队列，立即返回
  └─ deliver_message(from, to, msg)
       ├─ 查 g_local_users
       │   命中 → async_call("on_message")，零网络
       ├─ 查 g_location_cache
       │   命中 → RPC remote_deliver，零 Redis
       └─ Redis HGET → 回填缓存 → RPC remote_deliver

// 后台独立线程：
batch_saver 线程
  → wait 100ms 或 batch ≥ 50
  → BEGIN + INSERT × N + COMMIT (MySQL)
```

**对比阶段四，单次消息的路径变化**：

| 步骤 | 阶段四 | 阶段五 |
|------|--------|--------|
| user_exists | RPC（网络等待） | **去掉** |
| seq_id | Redis INCR（网络等待） | **Snowflake 本地生成** |
| 消息存储 | RPC + SQL INSERT（网络等待） | **内存入队，立即返回** |
| 用户位置 | Redis HGET（每次都查） | **本地缓存优先，零 Redis** |
| 总网络往返/条 | 3-4 次 | **0-1 次** |

### 面试 FAQ

**Q: 批量写入如果宕机，丢多少消息？**

> A: 最多 50 条。消息入内存队列后就返回了 seq_id（客户端认为发送成功），flush 线程负责写入 MySQL。如果服务器在攒批期间宕机，这批消息就丢了。项目定位是 IM 场景，少量丢消息可接受。如果要保证不丢：① WAL 日志，先写磁盘再回客户端；② 双写到本地 + 远程，确认落盘再返回。

**Q: 连接池为什么是 16？**

> A: `std::min(hardware_concurrency(), 16)`。本机 16 核就 16 个。压测时 MySQL 在 20K QPS 下 CPU 未饱和，16 连接够用。如果后续瓶颈转移到 MySQL，可以调大连接池 + 升级 MySQL 配置。

**Q: 为什么最优并发数是 16（CPU 核心数）？**

> A: 因为 server 用的是 Reactor 模型，32 个 io_context × 1 线程/io_context。当并发连接数 = 核心数时，所有 CPU 核都被占满，再增加连接只会增加上下文切换开销，不会提升吞吐。这个结论是通过扫描 1/2/4/8/16/32/64/128/256 连接数验证的。

**Q: 20K（离线）和 10.8K（跨节点）为什么差一倍？**

> A: 离线场景的消息只走到 `deliver_message` → 查 `g_location_cache` 发现不在线 → 结束。全部本地操作，无网络开销。跨节点场景要经过 sender 节点序列化 + 网络传输 + receiver 节点反序列化 + 投递到接收连接 + 响应返回，多出来一次完整的跨机器 RPC。

**Q: echo 54K，消息转发才 20K，为什么差这么多？**

> A: 原因三个：① echo 只有一个 string 参数，消息转发有 from+to+msg+seq_id+timestamp 五个字段；② echo 不调 Snowflake 和 batch_saver.push；③ echo 不需要 deliver_message 的三级路由查询。54K 是框架基准的上限，20K 是业务链路的实际吞吐。

**Q: 压测里 echo 并发模式的区别是什么？**

> A: 三种模式：① echo（50 独立 io_context + 独立连接）——最适合纯吞吐测试，连接不共享，无锁争用；② echo_reactor（1 共享 io_context + 16 线程）——模拟真实服务端场景，共享线程池会有锁开销，QPS 约 31K 低于独立模式；③ echo_shared（50 线程抢 1 连接）——极端场景，14K QPS，说明连接粒度过粗时锁竞争严重。

### 架构演进总结

```
阶段一: client ←→ server（纯内存）
         ↓ 加持久化
阶段二: client ←→ server ←→ Redis（缓存 10 条）
                      ↓ (async)
                   SQLite（全量持久化）
         ↓ 加集群
阶段三: client ←→ server-node × N ── ZK / 手动配置
         ↓ 拆分存储 + 自动发现
阶段四: client ←→ Nginx ←→ server_node × N ─RPC→ sqlite_service → SQLite
                       ↑ Redis Pub/Sub 自动发现
         ↓ MySQL + 批量 + 缓存
阶段五: client ←→ Nginx ←→ server_node × N ────→ MySQL（批量异步写）
                       ↑                    ├─ Snowflake（本地 ID）
                      Redis Pub/Sub          ├─ g_location_cache（三级路由）
                                             └─ Docker 容器化部署
```
